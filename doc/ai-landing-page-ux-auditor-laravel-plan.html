AI Landing Page UX Auditor

Google Analytics tells you 62% of people leave. It never tells you why. This tool looks at your landing page the way a person does — it takes pictures of every section, reads them with an AI that understands design, then lines those pictures up against your real visitor numbers. The result is a short, ranked list of things to fix.

What the tool actually does

Four sentences, no jargon.

The problem today

A marketer opens Google Analytics and sees numbers: bounce rate 62%, CTA clicks 2%, scroll depth 35%. Those numbers describe what happened. Nobody can tell them what to change on the page on Monday morning.

What we build

A React dashboard on top of a Laravel backend. You paste a landing page URL once. Every week the app photographs the page, pulls your visitor numbers, asks an AI to judge both together, and hands you a to-do list sorted by how much money each fix is likely to make.

The one clever bit

The AI never looks at a screenshot alone. Each picture arrives with its own numbers attached — "82% of visitors saw this section, only 2% clicked the button." That pairing is what turns a design opinion into evidence.

Who uses it

Marketing and product people who do not write code. So the finished screen must be readable in two minutes with no training. That constraint drives every design decision later in this plan.

Step by step

The build, in the order you build it

Ten phases. Each one ends with something you can open in a browser and show to somebody. Do not start a phase until the previous "Done when" is true — that rule is what keeps the project from turning into seven weeks of invisible progress.

P0

Set up the workshop

Install everything, wire React to Laravel, prove the empty app runs.

4 days
  • Start a fresh Laravel 12 project on PHP 8.3.
  • Add PostgreSQL for data and Redis for the queue. A queue is just a to-do list the server works through on its own.
  • Add Laravel Sanctum for login. Sanctum lets a React app log in with a normal secure cookie — no token juggling, no refresh-token code to write.
  • Add a plain React 19 app in the same repo under resources/js, built by Vite (already in Laravel). Add React Router for the four screens, Axios for API calls, TanStack Query for loading and polling, and Tailwind for styling.
  • Install Node and Playwright on the server. Playwright is the robot browser that will take our screenshots.
  • Install Laravel Horizon so you can watch background jobs succeed or fail on a real screen.

One repo, two apps. Laravel does only two jobs — serve JSON at /api/*, and serve the React index.html for every other URL. React does all the screens. Keeping both in one repo means one deploy, one login and one place to look when something breaks; you still get a real React codebase you could split out later. Skip Inertia — it ties React back to Laravel routing, and you asked for a basic React app.

P2

Collect the numbers

Pull real visitor data from Google Analytics and Clarity.

1 week
  • GoogleAnalyticsService — uses the GA4 Data API. Fetches daily and weekly visitors, bounce rate, average session time, conversion rate, exit rate, and the device split (desktop / mobile / tablet).
  • ClarityService — fetches scroll depth, rage clicks and dead clicks. Rage clicks means a visitor clicked the same spot again and again because nothing happened. That is a strong sign something looks clickable but is not.
  • FetchAnalyticsJob — a background job that calls both services and writes one analytics_reports row per audit.
  • Plan B, build it now: Clarity's API is limited and may not give you everything. Add a CSV upload on the page settings screen so a human can paste the same numbers in by hand. The rest of the pipeline must not care where the numbers came from.
  • CTA click rate comes from a GA4 event on your button. If the client has not set that event up, the audit says "not measured" rather than guessing.

P3

Take the pictures

A robot browser photographs every section of the page.

1 week
  • Write a small Node script, scripts/capture.mjs. It takes a URL and returns image files plus a JSON list of what it captured.
  • Laravel runs that script with Symfony's Process class and reads the JSON back. Laravel stays in charge; Node only drives the browser.
  • How sections are found — three levels, in order:
    1. Use CSS selectors the user typed in (most accurate).
    2. If none, look for <section> tags and big landmark blocks.
    3. If that fails, slice the full page into equal horizontal bands and label them by position.
  • Capture at two sizes: desktop 1440×900 and mobile 390×844. Mobile is usually where the conversion is lost, so it is not optional.
  • Wait for fonts and images to finish loading, hide cookie banners, then shoot. A screenshot of a cookie wall teaches the AI nothing.
  • Save files to a storage disk (local in development, S3 in production) and write one screenshot_sections row per image.

You will create

  • scripts/ capture.mjs
  • app/Services/Screenshot/ PlaywrightRunner.php
  • app/Services/Screenshot/ SectionDetector.php
  • app/Jobs/ CaptureScreenshotsJob.php

  • Memory Chromium is heavy — 2 GB minimum on the worker box

P4

Let the AI look

Every picture gets a score and a list of problems.

1 week
  • One background job per section, run as a Bus::batch() so six sections are analysed at once instead of one after another.
  • Each call sends: the section image, the section's own numbers, the page's goal, and a strict instruction to reply as JSON only.
  • What the AI is asked to judge — layout (hierarchy, alignment, white space), the call-to-action button (visible, big enough, enough contrast, clear words), typography (readable, sensible sizes), design (colour consistency, image quality, mobile friendliness), trust (testimonials, logos, security badges), and content (headline clarity, value proposition, button wording).
  • Force the shape of the answer with a JSON schema. Then validate it in PHP before saving. If the reply does not match, retry once, then record a clean failure — never save half-parsed text.
  • Keep a token_cost column on every call. You want to know what one audit costs before a client asks.

You will create

  • app/Services/Ai/ VisionAuditor.php
  • app/Services/Ai/ AuditSchema.php
  • app/Jobs/ AnalyzeSectionJob.php
  • Model AiFinding
  • resources/prompts/ section_audit.txt

The AI's role

"You are an experienced conversion, UI/UX and digital marketing expert. Judge this section using both the image and the numbers. Say what is wrong, why users may not convert, what to change, and how much it matters."

Done when

Every section has a score from 0 to 100 and at least one specific, non-obvious problem written in plain language.
P5

Join the numbers to the pictures

The heart of the product. Everything else is plumbing.

1 week

Two passes, in this order. Rules first because they are cheap, repeatable and explainable. AI second, to catch what the rules missed.

  • Pass 1 — rules in PHP. Fixed patterns you can test and trust. See the table below.
  • Pass 2 — one AI call. Send all section findings and all metrics together, as text. Ask it to explain the drop-off story across the whole page — what the rules cannot see because they only look one section at a time.
  • Every insight must carry evidence: a metric, a number, and a section name. An insight without evidence is deleted, not shown. This is the rule that keeps the tool honest.

Why rules first

Rules are testable. You can write a unit test that proves "seen but not clicked" fires correctly. You cannot unit-test an opinion. Rules also make the AI cheaper, because you only pay for the hard part.

P6

Turn insights into a to-do list

Ranked by likely money, not by how loud the problem is.

4 days

Each recommendation has five parts, always in the same order, so people learn to read them fast:

  • Problem — one sentence. "The main button is hard to see."
  • Evidence — the numbers. "82% of visitors see the hero. 2% click."
  • Suggested fix — something a designer can do today. "Raise button contrast to at least 4.5:1 and move it above the fold."
  • Expected impact — honest and ranged. "CTA clicks 2% → 4–6%."
  • Priority — High, Medium or Low, calculated not guessed.

How priority is calculated. A score, so two people reading the same audit agree:

priority = (traffic share × severity × confidence) ÷ effort

Traffic share = how many visitors actually see that section. Severity = how badly it blocks the goal, 1–5. Confidence = how sure the evidence is, 0–1. Effort = a rough dev estimate, 1–5. A tiny problem on a section 90% of people see beats a big problem on a section 5% reach.

High  Medium  Low — three buckets only. More would be noise.

P8

Build the React dashboard

Four screens. Understandable in two minutes, with no training.

1.5 weeks

1 · Overview

The health score, visitors, bounce rate, conversion rate, and the change since the last audit. Plus the three highest-priority fixes, right there. If someone reads only this screen, they still know what to do.

2 · Analytics

Visitor trend over time, bounce rate, scroll depth by section, CTA click rate, desktop vs mobile. Charts, not tables.

3 · AI findings

One card per section: the screenshot on the left, the score, the problems and the suggested fixes on the right. Seeing the picture next to the words is what makes the advice believable.

4 · Priority tasks

The to-do list, grouped High / Medium / Low, each with a checkbox. Ticking one records who fixed it and when, so the next audit can measure the result.

Two rules for this screen. First, no metric appears without a sentence saying what it means. Second, every number is clickable and leads to the finding that explains it. A dashboard that only shows numbers is the exact problem this product was built to solve.

How React knows the audit finished. The audit takes two to four minutes, so the browser cannot just wait. Do the simple thing:

  • After POST /api/audits, React gets back an audit id and a status of pending.
  • TanStack Query re-fetches GET /api/audits/{id} every 5 seconds while the status is running, and stops on its own when it reads completed or failed.
  • The API returns a stage field — "taking screenshots", "analysing sections" — so the progress bar says something true instead of spinning.

Websockets (Laravel Reverb) would be nicer, but polling one endpoint every five seconds for three minutes is 36 tiny requests. Not a problem worth solving in V1.

Add a PDF export from day one. Agencies will send this to clients, and a link behind a login does not survive an email chain. Generate the PDF on the server with Browsershot — never in the browser, or the layout will differ per person.

P9

Automate and ship

Make it run every week without anyone pressing a button.

4 days
  • Laravel Scheduler runs every active page weekly, spread across the night so twenty audits do not start at once.
  • Email when an audit finishes, and email louder when the score drops more than five points. A falling score is the alert people actually want.
  • Horizon dashboard, failed-job alerts, and a retry button on the audit screen.
  • Rate-limit audits per page — one per day maximum — so nobody burns the AI budget by clicking Run audit twelve times.
  • Deploy: PHP-FPM + Nginx, a separate worker box with Chromium installed, Redis, and PostgreSQL. Screenshots on S3.
  • Two extra steps because of React. Run npm run build in the deploy script — the React app is compiled files, not source. And add a catch-all web route so that refreshing the browser on /audits/42 serves React's index.html instead of a Laravel 404. Forgetting that second one is the classic first bug of any Laravel + React app.

The contract

Where React and Laravel meet

Because the front end is a separate React app, this list is the seam between the two halves. Agree it in week one and both halves can be built at the same time — one developer on the API, one on the screens, without either waiting.

MethodEndpointWhat it doesUsed by
POST/login · /logoutSanctum cookie sessionLogin screen
GET/api/userWho am IApp shell, on first load
GET/api/pagesAll landing pages, with the latest score on eachPage list
POST/api/pagesAdd a page. Returns 422 with field errors if invalidPage form
PATCH/api/pages/{id}Edit URL, IDs or section selectorsPage form
POST/api/pages/{id}/auditsStart an audit. Returns the new audit with status pendingRun audit button
GET/api/audits/{id}Status and stage. The endpoint React polls every 5 secondsProgress bar
GET/api/audits/{id}/reportEverything at once: score, metrics, sections with screenshot URLs, findings, recommendationsAll four dashboard screens
GET/api/pages/{id}/historyScores over time, for the trend chartAnalytics screen
PATCH/api/recommendations/{id}Tick a fix as donePriority tasks
GET/api/audits/{id}/pdfServer-rendered PDF downloadExport button

One request per screen, not ten

/report returns the whole audit in a single response — roughly 60 KB of JSON. Four screens read from one cached result. Splitting it into ten small endpoints feels tidier and makes the dashboard visibly slower.

Screenshots are signed URLs

Never return a raw S3 path. Laravel returns a temporary signed URL that expires in an hour, so a leaked link does not expose a client's page forever.

Laravel API Resources, always

Never return $model. A Resource class is the only place that decides what React sees, so adding a database column can never leak it into the API by accident.

Errors have a shape

Every failure returns { message, errors? } with a real HTTP status. React has one Axios interceptor that turns any of them into a toast, and no component has to handle errors itself.

Before you write code

Eight things to decide

Each of these changes the plan. Answer them in week one, not week four.

  1. How do we find the sections of a page?Ask the user for CSS selectors, or guess automatically? Guessing is friendlier but less accurate, and inaccurate sections poison every step after. Recommendation: guess first, let the user correct it.
  2. Do we actually have Clarity API access?Microsoft Clarity's API is narrower than its dashboard. Confirm what it returns on a real account this week — heatmaps and click maps may need manual export.
  3. Is the CTA click rate being measured at all?It needs a GA4 event on the button. Most landing pages do not have one. If it is missing, the tool must say "not measured", never invent a number.
  4. One company or many?Single-tenant is faster to build. Multi-tenant means an agency can manage twenty clients. Decide now — retrofitting tenancy is expensive.
  5. What is the budget per audit?Six sections × two viewports = twelve vision calls, plus one correlation call. Set a hard ceiling in config and refuse to exceed it.
  6. How long do we keep screenshots?They are the biggest storage cost and may contain customer data if the page is behind a login. Ninety days is a sensible default.
  7. Are we allowed to screenshot this page?Fine for your own pages. If competitor comparison is added later, check terms of service and robots rules first.
  8. Same domain, or React hosted separately?Same domain is strongly preferred — Sanctum's cookie login just works, and there is no CORS to configure. If React must live on its own domain later, switch Sanctum to token mode and expect a day of work.

How far down the page people get before they stop. 35% means most never see the bottom two-thirds.

Clicking the same spot repeatedly because nothing happens. Usually means something looks clickable but is not.
Dead click
A click on something that was never interactive in the first place.

The part of the page you see before scrolling.

Single page app. Moving between screens never reloads the browser, so it feels instant.

React asking "is it finished yet?" every few seconds while the audit runs in the background.
